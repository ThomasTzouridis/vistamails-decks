## Tracking sheet (the one source of truth, read this before touching it)
Tab **Presentation Log**: one row per lead who is CONNECTED in the 16 live campaigns (already connected or connected back), keyed by LinkedIn id (column F). Leads who did not connect never get a row (they never get a message). Row order is stable: new connections are appended in first-seen order, do not sort, use a filter view. A lead who leaves the set (removed from the campaign) leaves the log.
- **Auto columns A:U**: rewritten every run from HeyReach and the tracker's own stamps: Lead, Company, Sender, Campaign, Copy, LinkedIn id, Connection status (HeyReach), Connected, First seen connected (own stamp), Message 1 due (connect + 3 h), Message 2 (deck) due (message 1 + 4 days), Message status (HeyReach), Replied (HeyReach), Campaign status (HeyReach), Last action (HeyReach), Company name (message 2, custom field `normalizedcompanyname`), Deck URL HeyReach sends (custom field `presentation`), Deck slug, Live check (200 = a VistaMails deck answers, else the HTTP code), **Check** (OK or the exact problem: DECK NOT LIVE, FAILED in HeyReach, inactive, "message 1 out, no deck", "waiting for message 1"), Note or error. DECK NOT LIVE and FAILED DM Thomas once per lead. Never edit these by hand.
- **Manual columns V:AC** (never touched by the script, Claude fills them from replies and meetings): Reply date, Reply summary, Interested, Meeting booked date, Showed up, Closed, Deal value, Notes. The manual block moves with the lead (keyed by LinkedIn id).
- **Tracking columns AD:AM** (written every run, one value set per deck slug, to every row of that slug): Deck opens, Deck sessions, First opened, Last opened, Deepest slide, Time on deck (s), Videos played, Book clicks, Meeting booked (Calendly) = date of an active booking matched to the lead, Opened from = visitor locations per session (City, CC via ipinfo.io; opens from Nepal are flagged "VistaMails?" because the client sits there).
- **Reading it**: Connected = Yes is who accepted; Check not OK is a lead HeyReach would send a dead link to; Replied / Interested / Meeting / Showed up / Closed give the funnel per sender, campaign, copy and company.

## Performance tab (hr_perf.py via jobs/vista_perf.py, daily 04:00)
- Automated columns B and D:F are all-time totals straight from HeyReach `GetOverallStats` per sender, overwritten every run, 0.0% format: B connection back = connectionsAccepted / connectionsSent; D reply = totalMessageReplies / totalMessageStarted; E interested = autoTaggedInterested / totalMessageStarted; F meeting booking = (inbox conversations tagged "meeting..." OR a Meetings tab row, per lead) / totalMessageStarted.
- Column C "Presentation open rate per messaged lead" is written by vm_track: messaged = message status not None AND a deck slug, opened = that deck has at least 1 counted open. Blank until someone is messaged.
- Three sections, set by header cells in column A: "All Campaigns" (every campaign of a sender), "Ecom Founders 500+ (1A / 1B with decks, from 2026-10-19)" (the 16 live campaigns), "Klaviyo campaigns (paused since 2026-09)". Under each header one row per sender (full name exactly as in HeyReach) plus "Total" (raw counts added, then divided). G onwards (show up, closing, deal value, LTV) is manual, never touched. Empty cell = denominator 0.
- Tab **Copy**: one row per copy (1A, 1B, Klaviyo Campaign 1, Klaviyo Campaign 2), B = the Google Doc with the full message chain (built and kept current by vm_track from the HeyReach sequence, same format as "Messages Craze & Friends": normal text, bold "Message N, ... later" lines, one empty line between paragraphs and messages, "Examples for Presentation" heading with company page and deck links), C:F the same four rates over the 8 campaigns that send that copy. G onwards is manual. A new copy needs one line in `COPIES` (vm_track) and `copies` (vista_perf).

## Deck tracking + bookings, the full pathway (vm_track.py, every 4 h)
**1. Booking link.** Our exclusive Calendly event type on Umesh's account: https://calendly.com/umesh-gps/vistamails-email-marketing-discovery-call (event type 827bbde0-a5da-4d5a-9604-e73b1d8de857, `CALENDLY_VISTAMAILS_BOOKING_URL`). Only bookings of THIS event type are ours; Umesh's own event types (Email Marketing Discovery Call, Strategy Call, Email & SMS) are his business and skipped. The PAT has no `users:read`, so the user URI is fixed in the script. Open flag 2026-10-19: the deck template's Book button still points at calendly.com/umeshpdy95/email-strategy-consutling (Umesh's own, no API), so a booking from a deck is invisible to the tracker until the deck link is switched to the umesh-gps link.

**2. How a deck reports.** Every deck (`_src/template.html`, every `<slug>/index.html`) carries one tracking `<script>` before `</body>` that sends beacons (`navigator.sendBeacon`, text/plain) to mac-hub `https://macbook-air-von-thomas.tail94ea31.ts.net/webhook/vm-deck-track` (hub.py appends every POST with the visitor IP to `~/Desktop/AIOS/automations/mac-hub/logs/events.jsonl`). Events per visit (one random session id): `open` (referrer, UA, width, timezone, slide count, phone), `slide` (new deepest slide), `video`, `book` (click on the Calendly link), `ping` every 30 s while visible, `leave`.

**3. Who is NOT counted.** Our PC and Mac on the tailnet (Chrome blocks the beacon). Any device of ours or the senders: open a deck once with `?vmint=1`, undo with `?vmint=0`. Bots and Playwright. Link scanners (LinkedIn / Microsoft Safe Links: data center IP, impossible ping clock, zero-width window, headless UA, `is_bot()`). Every session from Slovenia (IP country SI, else timezone Europe/Ljubljana, `NOT_COUNTED_CC`). Dropped sessions stay in the state file for the booking matcher only.

**4. Booking match.** Every active booking of our event type becomes one Meetings row with THE LEAD in column A, even when a colleague booked for them. Evidence: the deck tag (when the Book button carries `utm_source=vm-deck&utm_campaign=<slug>&utm_content=<session>`), the tracked session, every campaign lead's facts from HeyReach (32 campaigns, cached 6 h), the HeyReach inbox (who got the Calendly link or the deck link, who mentioned a partner), Supabase ocean_leads (emails and company domains), the invitee's timezone. Rules, first hit wins, the reason lands in column M as a plain sentence:
0. internal: email domain actiscale / vistamails or a team member's name (the 8 senders, Thomas, Umesh) -> row "INTERNAL: <name>".
1. deck tag: the deck's leads; booker is one of them by name or email -> that lead; one lead on the deck -> that lead ("booked by another person for this lead"); shared deck -> the one who got the message, timezone tie-break; session from Nepal / Slovenia and the booker is no lead -> internal.
2. email: booker email is a lead's email (HeyReach, then Supabase) -> lead. Work email domain = a lead's website, or Supabase knows the person and their company domain = a lead's website -> "booked by a colleague".
3. chat: booker name or email appears in a lead's HeyReach conversation -> that lead.
4. name: unique accent-free name match among all campaign leads (exact, missing part, initial, typo) -> lead.
5. plain link: leads sent the Calendly link in HeyReach in the last 30 days, timezone fit, newest first -> best guess, CHECK.
6. timing: a deck opened or Book clicked within 2 h before the booking whose session timezone fits -> best guess, CHECK.
7. nothing: "<name> (no lead match)", CHECK; timezone Kathmandu / Ljubljana -> INTERNAL.
**Two more meeting sources (the Symonds model):** a HeyReach tag containing "meeting" on a lead (set in the inbox when a meeting was agreed in chat, or elsewhere than our Calendly link), and a date typed into Presentation Log "Meeting booked date" (column Y). Both land as one Meetings row keyed by the lead id (K), M = the source sentence, H = the LinkedIn thread text. The Calendly row wins when both exist.
**Every row fills itself (`enrich_row`, Thomas: fully automatic, never ask).** On every run every Meetings row (new and old, INTERNAL skipped) gets each empty cell of B email, C website, D LinkedIn, E company LinkedIn, F phone filled, filled cells are never touched. Sources in order: what Calendly put in the row (reminder number / phone question), the HeyReach lead profile, the list custom fields, Supabase `ocean_leads` (email, domain, company LinkedIn, person_phone, company phone), then Prospeo `POST /enrich-person` with `enrich_mobile` (10 credits per revealed mobile, email + website + company LinkedIn free with it, 0 on a miss, same person free again for 90 days). Prospeo is only asked while F is empty, waterfall LinkedIn URL -> work email -> name + company website; a personal mobile wins, the company HQ line is the fallback, Supabase company phone last. Cached per lead in the state file `phones`, a miss is retried after 30 days.
**Booked lead: sequence stop, tag, Supabase, Slack.** For every active meeting matched to a lead, three steps run once, each retried every run until it worked (state `acted[lead] = {stop, tag, sb}`, a failure DMs Thomas): `StopLeadInCampaign` in the lead's campaign, `POST /lead/AddTags` "Meeting booked", Supabase `ocean_leads.mailvista_status = 'meeting booked'` with phone / email / domain gap-filled and `matched_sources` += "VistaMails Calendly booking <date>" (or "VistaMails meeting (HeyReach tag ...) <date>"), a lead the DB does not have yet is inserted (append-only). Slack #meeting-booked-notifier: a Calendly booking of our event type is posted by the booking-tracker (Vercel, `automations/booking-tracker`, vistamails entry) already, so vm_track posts only tag / typed meetings (state `slacked`, once per lead). A new meeting also runs vista_perf right away, so the Performance tab meeting rate never waits for 04:00.
**Runs clean or tells Thomas (self-check).** At the end of every run `issues_of` lists what is still undone: a booked lead with stop / tag / Supabase still open after the retry, a booking that matched no lead (needs the Lead override in Meetings N) or whose override matches nobody, a tag meeting without its Slack post, a source that threw during enrich. `report` DMs Thomas once per run at most: NEW, STILL OPEN after 24 h (7 days for an unmatched booking), resolved. A crash goes through `crashed`: traceback in the job log, one DM, at most once per 20 h (`_private/vm_track_crash.json`). No Status tab (Thomas 2026-10-17). Reschedules keep the original row (key = root invitee, G updated), cancels get " (canceled)" in G. Column N "Lead override": type the lead's name there and the Presentation Log uses that lead; the row itself is never rewritten.

**5. What lands where (all automatic, every 4 h).** Presentation Log AD:AM per deck slug (see above). Meetings tab: A:G the lead (name, email, website, LinkedIn, company LinkedIn, phone, event date), H Conversation (LinkedIn thread for tag meetings, else manual), I:J manual, K key (Calendly root invitee URI or lead id), L Booked by (if not the lead), M Matched by, N Lead override. Performance C per sender and Total in every section. Copy B the doc links.
